## TieZ 与 Witch Clipboard 对比分析

对本地工作目录（TieZ / jimuzhe/tiez-clipboard）与 https://github.com/witchscottishfoldcat/WitchClipboard 做了源码级对比。

**本地项目事实（用于后续判断基线）**
- 本地目录是上游 master 的快照，**没有 .git**，无法直接 diff 或跟进上游；版本 0.3.4（`src-tauri/tauri.conf.json`、`Cargo.toml`、`package.json` 三处一致）。
- 代码规模：Rust 25,940 行 / 57 文件；TS/TSX 23,749 行。Rust 约 70 个单元测试，集中在 `services/clipboard/utils.rs`(47)、`services/auto_tag.rs`(9)。
- 前端功能模块：app / clipboard / emoji / file-transfer / settings / tag / theme-store。
- **数据库是明文 SQLite**（`rusqlite` bundled + WAL，无 SQLCipher），加密仅 `infrastructure/encryption.rs` 的 DPAPI 单值封装（WebDAV 凭据等）。
- **搜索没有 FTS5**：`clipboard_repo.rs:959` 的 `search()` 是 trim + to_lowercase 后匹配，历史量大时性能和中文检索都吃亏。
- 无 `scripts/` 目录、无 selftest、无系统剪贴板 E2E；CI 只有 `.github/workflows/release*.yml`（主发布流程 matrix 仅 windows-latest）。
- 上游元数据：GPL-3.0（Copyright 2026 LongDz），2,697 star / 121 fork / 48 open issue，创建 2026-03-09，最后 push 2026-07-29。

**Witch Clipboard 事实**
- 2026-07-26 创建，PolyForm Noncommercial 1.0.0，3 star / 0 fork / 0 issue，版本 1.7.2，最后 push 2026-09-10。
- 仅 Windows（x64 正式 / ARM64 实验），SQLCipher 全库加密 + AES-256-GCM 图片，FTS5 trigram 中文检索，E2E 加密 WebDAV，selftest + 系统剪贴板 E2E。
- 与 TieZ 技术栈（Tauri 2 + Rust + React 19 + TS + Tailwind 4 + Vite 7）、双面板设计、局域网二维码传输、WebDAV 同步、CF_HDROP 文件处理高度重合，**同源迹象明显**；但许可协议不同，若确有代码继承关系存在合规风险，已提醒用户自行核实。

**结论**：TieZ 胜在平台覆盖（含 macOS）、功能广度、社区规模、许可宽松；输在数据加密、检索能力、测试验证体系、上游更新节奏。

## 移植 FTS5 中文搜索（用户选定：只做这一项，其余不动）

**前提发现**：`libsqlite3-sys 0.28.0` 的 bundled 构建已带 `-DSQLITE_ENABLE_FTS5`，SQLite 3.45 支持 trigram 分词器 → **零依赖改动**即可做。

**实测结论（Python sqlite3 探针验证）**
- trigram 默认**大小写不敏感**；中文 3 字以上可子串匹配，1~2 字返回空。
- 整个词加双引号做 phrase 查询 = 子串匹配；内部 `"` 需写成 `""`，可安全吃掉 `* % ( )` 等 FTS5 操作符。
- 列过滤（`source_app:xxx`）可用，但 2 字中文标签走列过滤搜不到 → tag_only 保持 LIKE。
- external content + `'rebuild'` 回填、INSERT/DELETE 触发器增量同步均验证通过。

**改动**
1. `src-tauri/src/infrastructure/repository/migrations.rs`
   - 新增 migration 12 + `create_search_index()`：建 `clipboard_fts`（fts5，content='clipboard_history'，content_rowid='id'，tokenize='trigram'）+ 三个触发器（ai/ad/au）+ `'rebuild'` 回填。
   - **失败即 DROP 掉半成品**（空索引会让搜索静默返回空，比没有索引更糟），且不记录版本号，下次启动重试。
   - `portable` 构建跳过索引（其 search 分支刻意保留 LIKE）。
   - 需 `use crate::error;`。
2. `src-tauri/src/infrastructure/repository/clipboard_repo.rs`
   - 新增 `FTS_MIN_TERM_CHARS=3`、`fts_index_available()`、`fts_phrase()`。
   - `search()` 步骤 1 增加 FTS 分支：非 tag_only 且词长≥3 且索引存在才走 MATCH，否则回落原 LIKE；参数按需走 `fts_phrase` 或原词。
   - **运行时查 sqlite_master 判断索引是否存在**，所以索引缺失时自动降级，不会报错。
   - 步骤 2（敏感/加密条目的解密扫描）**完全未动**。
   - 新增 `search_index_tests` 模块（12 个测试）。

**验证**：`cargo test --bin tiez-app` → 83 个测试中 81 通过、0 警告；新增的 13 个（12 + migrations 回填 1）全绿。
2 个失败是 `app::window_manager` 的既存坐标用例，与本次改动无关。

**有意未做的**：SQLCipher 全库加密（需换依赖 + OpenSSL + 旧库迁移）、selftest/E2E 体系 —— 用户明确只要 FTS5。

### 性能实测（50000 行，Python sqlite3 3.53 同 schema 基准）
建索引一次性耗时 401 ms / 5 万行。单次查询耗时：

| 查询词 | LIKE | FTS | 提速 |
|---|---|---|---|
| 配置接口地址（中文） | 15.4 ms | 0.054 ms | **284x** |
| 同步策略缓存（中文） | 14.6 ms | 0.034 ms | **429x** |
| tiez.name666 | 15.4 ms | 5.4 ms | 2.9x |
| cargo test | 14.8 ms | 6.3 ms | 2.4x |
| pytest | 15.1 ms | 4.2 ms | 3.5x |

中文等高选择性词收益最大（两个数量级）；命中率高的常见英文词只有 2~3 倍
（要回表查很多 rowid）。查询计划：`SCAN ch`（全表扫）→ `SCAN clipboard_fts VIRTUAL TABLE INDEX 0:M3` + `SEARCH ch USING INTEGER PRIMARY KEY`。
注意：LIKE 在 5 万行时是 15 ms，量级到 50 万行会到 ~150 ms，搜索框边打边搜才会明显卡。
